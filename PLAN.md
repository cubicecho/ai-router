# ai-router — plan

One self-hosted service that gives every app on a network **agents**, through one address, with
one key per app. An agent is a model, a prompt and tools defined once as a `cubicecho.agent/1`
document and used by any app. The router keeps the models and MCP servers its agents use, and
serves only agents: apps that want raw models or tools keep using llm-router and mcp-router.

Define "Personal Finance" once. Then chat with it in `min-agent`, and have `task_server` run it
every Friday, with the same prompt, tools and RAG behind both.

The concepts and rules are in [`.agents/domain-model.md`](.agents/domain-model.md). This file is
the order of work and the reasons for it. Phases 1 to 3 and 5 to 7 are built.

## Decisions

| Decision | Chosen | Why |
| --- | --- | --- |
| Repo | One new repo, `ai-router` | The two routers share a skeleton whose copies have drifted: `config/store.ts` is 339 lines against 513, and `http/app.ts` differs in nearly every line. A third copy for agents would make it worse |
| Old repos | Left as they are, and **they stay in service.** Their model and tool code is ported here for the agents' own use, not moved, and nothing standalone is published from here | ai-router serves agents only, so apps that run their own loop still need llm-router and mcp-router |
| Agents only | **ai-router's apps get agents and nothing else.** Its providers, pools and MCP servers are internal, used by agent runs. There are no endpoints for raw models or tools (an earlier plan had them under `/bare`) | Agents don't need the doors, only the areas behind them. `/bare/mcp` alone would have been an MCP server merging every server's tools, with its own sessions and elicitation forwarding. Decided after phase 1 |
| Shape | **One application**, laid out as the cubicecho **single-operator service** (the `cubicecho_backend` skill), with no tenancy. Areas are folders, not packages or plugins | It's the org's standard. With no standalone builds, a module interface would have one user |
| Users | **Several people share one router, and roles are the only difference.** An admin may do everything. Other users may do everything except secrets, settings and roles. Any user creates workspace keys and promotes revisions. **People use sessions only. The only keys are workspace keys, for apps** | A household or a small team uses one router. Ownership per row would be the multi-user archetype, a much bigger change for no need |
| Sign-in | **OIDC** (heautou, paired as in the backend skill's `sso.md`). No magic links, no SMTP, no passwords. The first user to sign in becomes admin. **Anyone the provider lets through may sign in.** Who that is gets decided in heautou, by group, never by a list in the router. **Under `SECURE_LOCAL_NET`, whoever opens the UI is signed in as the admin automatically.** That's all it does: apps still need a workspace key. This is narrower than the backend skill's version, where you type an address and a keyless request is let through | A link needs a mail server, and a password needs someone to reset it |
| Storage | **Postgres, always.** PGlite runs only in the tests, and a local Postgres from `npm run db:up` serves development. Drizzle tables, with migrations committed | Keys, run history, usage, revisions and joins between workspaces and their members all want a database |
| Admin API | GraphQL at `/graphql`: CRUD generated by drizzle-graphql, hand-written mutations, graphql-casl permissions, and a whitelist on writes | The standard |
| Endpoints | **`/v1` is the agents endpoint: its model list holds only agents.** `/runs` gives a run's record and events. `/mcp` is kept for agents offered as MCP tools, later | An app pointed at `/v1` sees agents and nothing else |
| Scope | **The key decides what an app sees.** One request carries one key, and a key belongs to one workspace. There are no `/w/<slug>` routes | The standard reads the caller from the credential, never the URL. Hermes picks profiles by URL and leaks state between them |
| Key header | `Authorization: Bearer` or `x-api-key`. Both may be sent only if they match | OpenAI and MCP clients send Bearer, and the standard uses `x-api-key` |
| Key storage | **The router's own `workspace_keys` table**, not better-auth's api-key plugin. A key is `air_` and 32 random bytes; the table keeps its SHA-256, its first characters, its workspace, who made it and its expiry | The plugin ties a key to a user (or to its organization plugin), so a key would die with whoever made it, and it reads and writes the database on every request. Here a key is checked against the snapshot, in memory |
| Override policy | **Kept as a real thing in the database, with one seeded policy that every agent uses.** It lets an app add its own instructions, narrow the servers and set sampling settings (temperature, `top_p`, `top_k`, `min_p`, penalties, `max_tokens`, `seed`, `stop`). The model never changes: it's the one the agent was made with. There's no UI for policies yet | Sampling is task-specific, and the model is the agent's identity. Storing the policy as a row now means choosing per agent later needs no migration of the idea |
| Agent reach | An agent uses the models and servers its own document names. The workspace decides which agents an app may run. It may also **configure** the agent's servers for its own runs, but never add to them | Scoping in two places disagrees. `task_server` reached the same rule in its #21. Configuring per workspace lets one Personal Finance agent work on each person's own budget |
| Server entries | A workspace's server entry **configures** one of the router's servers for the agent runs that workspace starts: an account's credentials, env, args, headers, URL | So one Personal Finance agent works on each household's own budget |
| Where the loop runs | **In the router, always.** The app keeps only its UI, schedule, history and its own tools. (An earlier plan had a directory mode, where an app ran an agent's document itself; it needed raw models and tools, and went with them) | One loop for every app is what makes the same agent behave the same everywhere |
| App tools | The run **waits** for the app's answer and resumes as the same run. A follow-up that answers every handed-back call resumes it, and a partial answer is refused | An app's timeline shows one run with a pause, not a chain of runs |
| Agent edits | Every save is a **revision**. A user's saves go live. Saves by an app or a run are drafts until a user **promotes** them, by hand or with per-agent **auto-promote** | Agents may edit agents later (the admin server), with every change visible and reversible. Hermes agents rewrite their own `SOUL.md` with no record |
| Agent loop | `agent-core` `runAgentLoop`, with its `dispatch` calling the tools area's own instances | `agent-mcp-pool` would start a second copy of every server |
| A run's model calls | **In process.** The router layer gives every run an internal model address, and the run's `fetch` hands each call to the models area's own forwarding: the pool's lease, the provider's key and headers, streaming, and usage under the run's workspace and agent. `agent-core`'s endpoint `fetch` option (4.26.0, [agent-core#224](https://github.com/cubicecho/agent-core/issues/224)) does this | No HTTP door, no run token and no loopback rules. The forwarding is the same code a door would have used |
| Slim apps | **Apps keep calling `runAgentLoop`, and only the config changes.** It points at `/v1` with the agent's id, and carries an agent flag taken from the `/v1/models` entry (`ai_router.kind: "agent"`). With the flag, the loop forwards the router's run events, keeps its own compaction, preselection and on-demand loading off, and sends an idempotency key on retries ([agent-core#223](https://github.com/cubicecho/agent-core/issues/223)). Apps drop `agent-mcp-pool` and their own loop code, not `agent-core` | `agent-core` is already an OpenAI tool loop, and it keeps a server's tool-call ids as sent, so the app-tool hand-back works as it is. One call site, the same `dispatch` and `onEvent`, and the apps' Runs tabs stay as they are |
| Run events | `agent-core`'s `RunEvent`, carried unchanged, as JSON. `agent-core` has no encoder or decoder of its own for them (found in phase 7) | `min-agent`, `task_server` and telos already render it. AG-UI and Open Responses cover similar ground, and can be added as translators later |
| Conversations | Stateless, plus an optional `X-Conversation-Id`, stored as a row with a TTL | Every OpenAI-compatible surface surveyed does this, and a row survives a restart |
| Admin tools | Later, as a built-in **admin server**, `ai-router`, built with `@cubicecho/graphql-mcp`. It's the only way in: a workspace gets it through a server entry with permission levels, and an agent must name it. There's no separate `/admin/mcp` | It answers "why did Friday's run fail?" and lets agents draft agents. With only workspace keys, a second door would need a second set of permission checks |
| Discovery | **Later.** The AI Catalog, Agent Cards, and LAN announce and discovery are not in the first pass. When they come, the public catalog names only the router's endpoint, and the agents behind it are listed only to a key | Simpler first pass. mcp-router serves its catalog and cards to anyone, which here would show every agent on the network |
| Untrusted code | **Each MCP server runs as its own user, through a purpose-built helper, `run-as-child`** (`docker/run-as-child.c`). The helper is the only thing in the image with any capability, and holds only `CAP_SETUID` and `CAP_SETGID`. It switches only into the id range 10000–19999, never root or the router. It drops every capability, sets no-new-privileges and then runs the server. The router itself holds none. Install scripts (`npm install`, `uvx`) run as the server's user too | A combined router puts every provider key next to code installed from npm and PyPI. The phase 0 spike showed the simpler options fail or overreach. With `USER node`, Docker gives the router no capabilities at all, so it can't switch users itself. A general `setpriv` with those capabilities lets the router become root with full capabilities |

## Prior art

Researched November 2026: Hermes Agent, Open WebUI workspace models, LibreChat Agents API,
LiteLLM A2A, Letta, Docker cagent, Copilot `.agent.md`, Claude Code subagents, A2A v1.0, Agent
Protocol / ACP, OpenAI Responses.

The common pattern is `/v1/models` listing agents and `model: "<agent>"` running one with
server-side tools. Hermes, Open WebUI, LibreChat and cagent all do this. What we keep or avoid:

- **Hermes's agent is a stateful folder** holding config, `.env`, memory and sessions. Its agents
  rewrite their own prompt, and its profiles leak state through shared URLs. **Ours is a document
  with revisions, and a user promotes any change an agent makes.**
- **Open WebUI drops every server-side tool once a request carries `tools`.** **We keep them and
  add the app's tools beside them**, as LibreChat does on Responses. A name clash is refused.
- **cagent's `X-Conversation-Id`, with 409 on an overlapping run**, is the model for
  conversations.
- **No surveyed project declares what a caller may override.** The override policy is new here.
- **No other format puts a side task on a different model and endpoint.**
- **`${VAR}` interpolation is ruled out**, because of the spec's confused-deputy argument.

## Interfaces

| Path | Who | Serves |
| --- | --- | --- |
| `GET /v1/models`, `/v1/models/<id>` | key | the workspace's agents, and nothing else. Each entry carries its description, `context_length` when known, and `ai_router: { kind: "agent" }` |
| `POST /v1/chat/completions` | key | a run of the agent named in `model` |
| `POST /v1/<other>` | key | refused until `/v1/responses` arrives for agents |
| `/runs/<id>`, `/runs/<id>/events` | key | a run of the key's workspace, and its `RunEvent`s, as JSON or as a live event stream |
| `/graphql` | user | the admin API, used by the UI, with admin-only parts |
| `/mcp` | — | kept for agents offered as MCP tools, later |
| `/healthz` | anyone | health check |
| `/oauth/callback` | browser | a remote server's login |

- **Keys:** a workspace key sees its workspace.
- **Sessions:** a user's session sees everything enabled. The UI uses this, for example to try an
  agent.
- **Neither:** a request with neither is refused, on a trusted network too.

### Tables

| Area | Tables |
| --- | --- |
| auth | better-auth's `users` (with `role`), `sessions`, `accounts`, `verifications`; `oidc_settings`, the paired provider |
| router | `settings`, a single row |
| models | `providers`, `pools`, `pool_targets`, `usage_counts` (all internal: used by agent runs) |
| tools | `registries`, `servers`, `server_secrets`, `activity` (all internal) |
| agents | `agents` (with `override_policy_id`), `agent_revisions`, `override_policies` (seeded with one default row), `runs`, `run_events`, `conversations` |
| workspaces | `workspaces`, `workspace_keys`, `workspace_agents`, `workspace_servers` (env, args, headers and URL overrides for the workspace's agent runs) |

Notes:
- **Secret columns are excluded from GraphQL**, and each has a write-only mutation
  (`setProviderApiKey`, `setServerSecret`). Reads answer `apiKeySet: boolean`.
- **A revision's `document` is `jsonb`, stored as received**, so keys from a later 1.x survive.
- **`runs`, `activity` and `usage` have retention periods.** Usage days older than the detail
  window fold into the totals.

| Section | min-agent |
| --- | --- |

### An agent

```markdown
---
spec: cubicecho.agent/1
id: personal-finance
name: Personal Finance
description: Budgets, bills and the weekly money summary.
model: { model: "ollama/qwen3:32b", temperature: 0.3 }
tools: { servers: ["actual", "finance-docs"], maxIterations: 20 }
tasks: { title: { model: "ollama/qwen3:0.6b" } }
---
You help me run my household money. I budget monthly in Actual …
```

- **No `endpoint`:** the agent runs on this router's own models. A model id is
  `<provider>/<model>`, split at the first `/`, or a pool's name.
- **The router layer** sits underneath the agent and sets its endpoint to the router's internal
  model address, which the run's calls reach in process. Without it, an agent with no `endpoint`,
  and its side tasks, resolve to an empty address and can't run (found in phase 0).
- **Layers:** the router turns the request's leading system messages into a `host` prompt part,
  and `ai_router.task` into a `task` part. Both come after the agent's own parts, joined with
  blank lines. `host` and `task` are reserved, so an app can never replace one of the agent's
  parts, and an agent that uses either id can't be saved. A resumed run keeps its original host
  and task text.
- **The override policy is not in the document.** It's a row in the router, so the document stays
  portable to any host of the format.

### What an app sends and gets back

- **Request options.** An optional `ai_router` object in the request body, for apps that know
  the router. Standard clients never send it.
  - `task`: the text of a task layer, instead of folding the task into the user message.
  - `progress: true`: turns progress events on.
- **Sampling settings** go where any OpenAI client puts them: `temperature`, `top_p`,
  `max_tokens`, `seed`, `stop` and the penalties at the top level, and `top_k`, `min_p` and
  `repeat_penalty` at the top level too, as llama.cpp and vLLM take them. They form the request
  layer and apply to the agent's main model, never to its side tasks. `temperature` becomes the
  model's temperature and `max_tokens` its ceiling. Only the rest go into `extraBody`, because
  `agent-core` lets an `extraBody` temperature quietly beat the real one
  ([agent-core#222](https://github.com/cubicecho/agent-core/issues/222)).
  - **A sampling field the app didn't choose must not be sent.** Today `runAgentLoop` always
    sends a temperature, filled from the host's default, so every app would override the
    temperature the agent was tuned with. Under the agent flag it sends only what the host set
    for that call ([agent-core#223](https://github.com/cubicecho/agent-core/issues/223#issuecomment-6967515889)). A field the policy doesn't
  allow is refused with an error that names it.
- **Other standard fields:**
  - `response_format` is allowed by the default policy, because JSON output is task-specific.
  - `parallel_tool_calls` passes through to the agent's model.
  - `user` is recorded on the run, for the app's own reference.
  - `n` above 1 is refused, because a run gives one answer.
- **`Idempotency-Key`** on a request makes a retry safe: a repeat of a key answers with the run
  it already started, never a second run. `runAgentLoop` sends one when its config has the agent
  flag.
- **`X-Run-Id`** comes back on every agent response, so an app's own log can link to the
  router's run record.
- **App tools.** An app keeps its own tools (`task_server`'s "create a task", `min-agent`'s
  "ask the user") and sends them in `tools`.
  - When the agent calls one, the run hands it back and waits.
  - The app runs it and sends the result, and the same run resumes. That is the ordinary OpenAI
    client tool loop, not `agent-core`'s.
  - A run that waits past its timeout expires. The timeout is a `RUN_DEFAULTS` value, and it
    has to be generous enough for tools that wait on a person, such as `min-agent`'s "ask the
    user".

### Apps keep their detail

`min-agent`'s chat, and `task_server`'s and telos's Runs tabs, show each step, tool call and
result today. They must still show them when the agent runs in the router. All three already
render `agent-core`'s `RunEvent`, so **the router sends exactly those**.

- **Live, in the stream.** With `ai_router.progress: true`, the stream carries progress chunks
  between the content chunks:
  ```json
  { "object": "chat.completion.chunk", "choices": [], "ai_router": { "event": { "kind": "tool-call", "...": "..." } } }
  ```
  - An empty `choices` is the same shape as OpenAI's own usage chunk, so standard clients
    already skip it.
  - The `event` is an `agent-core` `RunEvent`, with `runId` set to the router's run id. It
    covers steps, reasoning, tool calls and results, side tasks, compaction, artifacts and usage
    per step.
- **Live, without streaming.** A non-streamed response with `progress: true` carries
  `ai_router: { runId, events }` beside `choices`.
- **Afterwards, by id.**
  - `GET /runs/<id>` gives the run: agent, revision, status, timings, usage and error.
  - `GET /runs/<id>/events` gives every event. With `Accept: text/event-stream` it follows a
    live run, which also lets an app watch a run it didn't start, from its Runs tab.
  - An app can keep only the id from `X-Run-Id` and fetch the detail later. It can also copy the
    events into its own run tables, as `task_server` and telos do with their own runs today.
- **App tools appear as events too**, so a handed-back call shows in the app's timeline like any
  other.
- **Scope:** a key reads only the runs of its own workspace.

## First release

**The first release is agents** (phases 1–3 and 5–8): the use case below, and `min-agent` chatting with
Personal Finance. The old routers keep serving apps that want raw models and tools.

## Use case: two agents for `task_server`

The acceptance check for the first release.
1. **Add MCP servers:** `actual`, `finance-docs`, `github`, `git`. **Add providers:** `ollama`,
   `openai`.
2. **Add Personal Finance:** `ollama/qwen3:32b` with servers `["actual", "finance-docs"]`.
3. **Add Coding Work:** an `openai/…` model with servers `["github", "git"]`.
4. **Add the `task_server` workspace**, with only those two agents and one key.
5. **`task_server` points at `http://router:3000/v1` with the key.** `GET /v1/models` answers
   `personal-finance` and `coding-work`, and nothing else.
6. **A `task_server` agent profile** names `personal-finance` with **`servers: []`**, so it adds
   no tools and no second loop around the agent's. A Friday task sends `task_server`'s system
   prompt, which becomes the `host` layer, and the task's text in `ai_router.task`.
   **Walked against `task_server`'s code in phase 0: this step doesn't work yet.** A profile's
   empty `mcpServerIds` means *every* enabled server, not none, so `task_server` can't say
   `servers: []` today. Its MCP tools would reach the agent as app tools. Phase 8 fixes it on
   `task_server`'s side: a profile that names a router agent sends no MCP tools.
7. **The run is recorded in the router** under workspace `task_server` and agent
   `personal-finance`. `task_server` asks for progress, so its Runs tab shows every step and tool
   call as it does today. It keeps `X-Run-Id` to fetch the detail again from `/runs/<id>`.

## Phases

0. **Model and paper check.** Review `.agents/domain-model.md`. Resolve `personal-finance` by
   hand three ways: alone, with a `min-agent` host layer, and with a "Friday" task layer. Walk
   the two use cases above against the model. Settle the open questions below that block
   phase 1.
1. **Scaffold. Done.** The single-operator service layout, following the `cubicecho_backend`,
   `cubicecho_typescript` and `coding-standards` skills.
   - **`core/` and `http/`:** the standard foundation.
   - **`db/`:** Postgres (PGlite only in tests), migrations, waiting for Postgres, the
     Postgres advisory lock, and the snapshot.
   - **`auth/`:** sign-in through OIDC, the trusted-network admin sign-in, the first admin and
     roles, workspace keys, the caller and the header rule.
   - **`graphql/`:** schema, permissions, operation limits.
   - **Workspaces:** the tables and keys.
   - **UI:** the web shell on cubeui with GraphQL codegen.
   - **Release:** CI's three jobs and the Docker image.
   - **Child isolation:** build `run-as-child` into the image from the spike's source.
     - **Preflight:** at boot, check that the helper can switch into the range. If it can't, refuse
       to start stdio servers with an error that says why. Running the container with
       `no-new-privileges` turns file capabilities off, which is the case the spike found.
     - **Running outside Docker:** without the helper (`npm run dev` on a laptop), children run
       as the router's own user, with a warning at boot. That's refused when
       `NODE_ENV=production`.
     - **CI:** the boot job runs the spike's checks against the real image.
2. **Models. Done**, internal: what agent runs call. Port llm-router's providers, pools, balancer and
   affinity, its forwarding (as a function, not an HTTP door), model listing for the UI, usage,
   and the GraphQL admin with its UI pages. Reviewed with the user:
   - **Kept from llm-router:** OpenAI-compatible providers only, with no translation. Model lists
     discovered live from each provider's `/models`, cached 60 s, failures not cached. A call is
     forwarded with only `model` rewritten, and a stream is passed through with usage read from
     it. Pools: least-busy (default), round-robin or random, sticky affinity by rendezvous
     hashing, an optional `maxLoadFactor`, leases in memory.
   - **Changed for the router:** provider keys are write-only secrets that answer `apiKeySet`;
     usage has an agent column, filled from phase 6; the routing tables are in the snapshot, so
     the file watcher and "reload" go.
   - **llm-router's bugs, fixed in the port:** a lease taken before the `try` that frees it can
     leak; round-robin keeps a stale turn when a pool's targets change; the sticky key is the
     whole opening of a conversation as JSON (hash it as it is read); usage days are in local
     time (use UTC).
   - **Kept on purpose:** two pools that share a target share its in-flight count, since it is
     one server's load.
   - **Usage outlives its provider:** a usage row keeps the provider's name as text, and its
     `provider_id` is an optional foreign key, set to null when the provider is deleted.
   - **The response timeout** (10 minutes until the first byte) is a `defaults.ts` value, not
     an editable setting, until something else needs runtime settings.
   - **Tables:** `providers` (name, display name, description, enabled, base URL, `api_key` as a
     write-only secret, `headers`), `pools` (name, display name, description, enabled, strategy,
     affinity, `max_load_factor`) and `pool_targets` (pool, provider, model, position).
   - **Admin API:** generated CRUD, checked by hooks and rebuilding the snapshot on commit, plus
     `setProviderApiKey` (admin only), `setPoolTargets` (the whole list, in order, in one
     transaction), `providerModels(id, refresh)` and `poolLoad(id)`.
   - **One name rule for every router name**, as both old routers have it:
     `^[a-z0-9][a-z0-9._-]*$`, at most 64. It replaces phase 1's stricter rule, workspace slugs
     included, so a name that works there (`llama.cpp`, `gpu_box`) works here. Servers (phase 3) also may not contain `__`.
   - **Providers and pools can be renamed.** The UI says which agents name the old model id,
     since their runs will fail until they are changed.
   - **Provider headers are visible in the UI** and any user may edit them, unlike the key. Apps
     never read them: a workspace key can't use `/graphql`, and `/v1` serves agents only. A header
     that holds a key (Azure's `api-key`) is shown to every user, so the key field is the place
     for a Bearer key.
   - **Forwarding is a function** (`models/forward`), not an HTTP door: a run's `fetch` calls it
     ([agent-core#224](https://github.com/cubicecho/agent-core/issues/224)).
   - **Usage:** one row per UTC day, workspace, agent, provider and model, with requests, input
     and output tokens. Counted from the provider's own numbers on a 2xx only: a stream's last
     usage chunk, or a JSON answer up to 8 MB. Days older than 90 fold into an all-time row.
     Counts gather in memory and are written every few seconds and at shutdown. A row keeps the
     workspace's and the provider's names, with optional foreign keys set to null on delete, so
     usage outlives both.
   - **UI:** Providers (list, add and edit, the key set by an admin, the live model list with
     refresh, usage per model and day), Pools (list, edit, an ordered target editor, strategy,
     affinity, load factor, live in-flight load), and usage on each workspace's page.
   - **Tests:** llm-router's balancer, affinity and usage-reader tests, ported; forwarding
     against a fake OpenAI server on loopback (streams, provider errors passed through,
     unreachable, the timeout, the caller aborting, a lease released on every path); the secrets
     test with a planted provider key.
3. **Tools. Done**, internal: what agent runs call. Port mcp-router's registries, the installer
   (running as the server's user), servers and their secrets, each server's user id from the
   child range and its own install folder, shared groups for servers that use mounted folders,
   a user id per workspace instance, instances (as the child user), server login, activity, and
   the UI pages. mcp-router's own MCP endpoint, its sessions and its discovery are not ported.
   - **Built and checked in the image:** a real npm server installed, listed, called and deleted
     as uid 10000, with the router refused its folder; and `scripts/check-children.sh` for the
     helper's group rules, a shared folder, and workspace instances.
   - **`run-as-child <uid> [-g <gid>] [-G <gid>,…] [--] <command> …`.** The helper itself refuses
     a uid or `-g` outside the child range, an extra group below 100 (root, shadow and every
     other system group), in the child range (another server's), or held by its caller (the
     router's own), a repeated group or option, more than 8 groups, and anything that isn't plain
     decimal. It sets exactly those groups, drops every capability, sets `no_new_privs`, and sets
     umask 022, so nothing a child makes is writable by its group unless it says so. Node checks
     the same rules in `tools/input`, so the UI says why first, and `ck_servers_extra_groups`
     holds them in the table.
   - **Shared groups, for a mounted folder.** A server's settings list extra groups
     (`servers.extra_groups`), such as `users` (100). Its instances run with them; its installs
     don't need them and run without. On the host, once: `chgrp -R users <folder>`,
     `chmod -R g+rwX <folder>`, and `find <folder> -type d -exec chmod g+s {} +`, so new files
     keep the group. With umask 022 a file the server creates is 0644, readable by the group but
     not writable: give the folder a default ACL (`setfacl -d -m g::rwX <folder>`) when the host's
     users must edit what the server writes. The group never reaches the server's own folder,
     which has the server's own group. For more isolation, run the server in its own container
     with the folder mounted, and add it as a remote server. Running it as the host user's id is
     ruled out: inside the container that's 1000, the router's own.
   - **A user id per workspace instance.** A server entry gets `workspace_servers.child_uid` from
     the same `child_uid_seq` when it is created, never reused. Its workspace instance runs as
     that uid with the server's uid as its primary group and the server's extra groups, so two
     workspaces' instances of one server can't read each other's `/proc/<pid>/environ` (their
     credentials) or signal each other, and the base instance can't read theirs.
   - **Folders.** Every folder is `<uid>-<random hex>` and holds `home/` (0700), the HOME of the
     programs that run as its uid. A server's install folder is 0750 with the server's own group:
     its packages, which its workspace instances can read but not write. Its `home/` is the base
     instance's alone. A workspace instance gets a 0700 folder of its own
     (`workspace_servers.install_dir`), made by its own uid on its first call, and starts in the
     server's install folder with that HOME. Deleting the entry, its workspace or its server stops
     the instance and removes the folder as its uid. Folders made before this change have no
     `home/`: reinstall those servers.
   - **How a child is handled without capabilities:** the router can't enter a child's folder or
     signal it. A child changes into its folder itself (`env -C` after the helper), and is
     stopped by closing its stdin, then by `process.kill` run through the helper as its own uid
     (the image has no `kill` program). Short commands run under GNU `timeout`, as the child.
4. **(Dropped.)** An import of llm-router's and mcp-router's configs. Providers, pools and
   servers are added in the UI.
5. **Agents: store. Done.** Agents and revisions, history and rollback, warnings, and the
   `override_policies` table with its one seeded default.
   - Also built: `workspace_agents` (which agents a workspace's apps may run), the agents in the
     snapshot for phase 6, and the UI: agents, a JSON editor with Check, history, and a
     workspace's agents.
   - An agent's name is its document's `id`, and can't change.
   - Postgres `jsonb` keeps a document's content but not its key order, so `spec` may not come
     first when it is shown again.
   - Not yet: the agent editor beyond JSON (phase 10), drafts and auto-promote (phase 9).
6. **Agents: runs. Done.** The agents endpoint `/v1`:
   - layers, the `ai_router` request options, override policy and reach;
   - dispatch to tools instances, and model calls in process through the models area, so usage
     counts them under the run's workspace and agent
     ([agent-core#224](https://github.com/cubicecho/agent-core/issues/224), in 4.26.0);
   - `Idempotency-Key`, so a retried request never starts a second run;
   - tool names a model accepts: OpenAI function names are `^[a-zA-Z0-9_-]{1,64}$`, but a
     server name may hold `.` and `<server>__<tool>` may pass 64 characters. Map or refuse them;
   - the runs table, `X-Run-Id`, the `runEvents` subscription, and usage per agent.

   Notes:
   - **Keys only.** `/v1` reads workspace keys and never a session, on a trusted network too.
   - **Refused for now:** `tools`, `tool_choice` and tool history (400, "app tools aren't
     supported yet"). `ai_router.progress` is accepted and does nothing until phase 7.
   - **`ai_router.servers`** is how a request narrows the agent's servers (`narrowServers`).
   - **Strict fields.** Any field the router doesn't read itself is an override, refused unless
     the policy's `sampling` lists it. The seeded policy names both `repetition_penalty` (vLLM) and
     `repeat_penalty` (llama.cpp). A field sent as `null` counts as not sent.
   - **The answer** is every turn's text, a blank line between turns, as streamed. Reasoning is
     not sent: progress events carry it in phase 7.
   - **Streams** send their headers, with `X-Run-Id`, at once, a comment every 15 s while quiet,
     and a failure as an `error` data line.
   - **Idempotency.** The hash leaves out `stream` and `stream_options`. A failed or cancelled run
     is answered again with its error (500, or 409 for cancelled), never run again. Keys are freed
     after 24 hours. A disconnect cancels a run without a key. A run with one goes on to its timeout,
     so the retry the key is for gets the answer.
   - **Elicitation** is declined: the router's MCP client offers no elicitation capability.
   - **Model calls** go through agent-core's `Endpoint.fetch` (#224, 4.26.0). Only endpoints at the
     router's model address get it, so an agent's own `endpoint.baseUrl` is still called directly.
     The forwarder keeps one `fetch` per workspace and agent, so agent-core's client pool and probe
     caches last across runs.
7. **Agents: app tools, progress events and conversations. Done.**
   - **App tools:** waiting runs, kept on the `runs` row and resumed by the call ids they handed
     back.
   - **Progress events:** `RunEvent`s in the stream, plus `/runs/<id>` and `/runs/<id>/events`,
     stored in `run_events`.
   - **Conversations.**

   Notes:
   - **Handing back.** An app tool is a `hostTools` entry whose dispatch answers with a stand-in
     and agent-core's `end`, so the loop stops after the step; the agent's own calls in that step
     still run. The app gets an ordinary answer, `finish_reason: "tool_calls"`, streamed or not.
     agent-core keeps a server's call ids, so the router mints the handed-back ids itself
     (`freshCallId`) and renames those calls in the answer, the events and the stored transcript.
     A repeated identical app call is handed back too (`dedupeToolCalls` skips app tools).
   - **Resuming.** A request whose trailing `tool` messages answer a waiting run's calls, matched
     by those ids within the key's workspace and the named agent, resumes it under the same run
     id. Every call must be answered, and nothing else. The run keeps its revision and layers:
     host and task text may be repeated or left out, and different text is refused; the resume's
     sampling and servers are ignored. Its `tools` replace the stored app tools when it sends any.
   - **Restarts.** A waiting run keeps its transcript, loaded tools, layers and the app's tools in
     `runs.resume`, so it survives a restart: a resume rebuilds the loop from them. Only `running`
     runs fail at boot. The token ledger isn't carried, so a resumed stretch starts a new epoch.
   - **Timeouts.** `RUN_DEFAULTS.waitTimeoutHours` (24) expires a waiting run, checked every 5
     minutes and on a late answer, which gets 409 `run_expired`. The run timeout counts each
     stretch's running time, not the wait.
   - **Name clashes are refused:** an app tool named like one of the agent's own tools gets a 400
     naming both, before the run is recorded, as are names the loop keeps (`load_tools`,
     `call_tool`, `record_artifact`). `tool_choice` may only be `auto`; legacy `functions` are
     refused.
   - **Idempotency.** A run answers to the key of its latest request: a resume takes over the key
     it sends (or clears it), so a retry of the resume gets its answer. A retry of an earlier
     request after a later one resumed the run is not recognised.
   - **Events.** The router numbers events itself, carrying on after the last stored one, since a
     waiting run outlives agent-core's in-memory bus and must never restart `seq`. agent-core's
     `stamp` isn't exported, so the router fills the same defaults. Every event is stored, token
     deltas included, written every 250 ms in batches, and `/runs/<id>/events` replays every one;
     `Run.events(folded: true)` joins text and reasoning deltas with agent-core's `fold`. A
     follower gets stored events, then live ones, with no gap and no repeat, and rejoins with
     `Last-Event-ID`. Following a waiting run keeps the stream open through the wait.
   - **Progress.** Events of this request's stretch of the run, as chunks with empty `choices`
     or `ai_router: { runId, events }`. A repeated `Idempotency-Key` answers without them.
   - **Token counts** are written as each turn's usage arrives, so a running run shows them.
   - **Conversations.** A row per workspace and app id, bound to the agent it started with, with
     the transcript of its last completed run (tool calls included) and its host text. With
     history, a request sends only new user or system messages; assistant or tool messages are
     refused, except the tool answers that resume its waiting run. One run at a time, held by a
     partial unique index; an overlap gets 409 `conversation_busy`. A failed run leaves the history
     as it was. Idle 72 hours, then pruned unless a run of it is going; its runs stay, naming none.
   - **GraphQL:** `Run.events(afterSeq, limit, folded)` in the `LiveRunEvent` shape, `runEvents`
     replaying stored events (with `afterSeq`), `Run.conversation`, `Conversation.runs`, and the
     statuses `waiting` and `expired`. `run_events` itself isn't generated.
8. **Consumers.** Each one keeps calling `runAgentLoop`, with a config pointed at `/v1` and the
   agent flag set ([agent-core#223](https://github.com/cubicecho/agent-core/issues/223) lands
   first). Each shows the router's events in the timeline it already has:
   - `min-agent`: "chat with an agent", rendering progress events in its chat.
   - `task_server`: a profile that names a router agent, with its Runs tab filled from the events
     or from `/runs/<id>`. Such a profile sends no MCP tools (today an empty server list means
     all of them), and no compaction or tool-select model.
   - telos: a lane whose agent is a router agent, with its Runs tab filled the same way.
9. **Admin server.** The built-in server `ai-router`, built with `@cubicecho/graphql-mcp`. Drafts,
   discarding and auto-promote arrive here, because this is the first way anything other than a
   user can save an agent. Decided 2026-11-18:
   - **Roles, not levels.** A workspace's entry for `ai-router` holds a set of roles, which add
     up. Each is a list of casl abilities, and every "manage" role includes reading its area:

     | Role | casl abilities |
     | --- | --- |
     | `agents:read` | read Agent, Revision |
     | `agents:manage` | read, create, update Agent, Revision |
     | `models:read` | read Provider, Pool |
     | `models:manage` | read, create, update, delete Provider, Pool |
     | `servers:read` | read Server, Registry |
     | `servers:manage` | read, create, update, delete Server, Registry |
     | `servers:operate` | read, operate Server (restart, try a tool, a server's login) |
     | `runs:read` | read Run |

   - **Actions are listed, never casl's `manage`**, which would grant any action added later
     (a `promote`, say) to every role that has it. A new action stays shut until a role names it.
   - **No role reaches** promoting or auto-promote, deleting an agent, secrets (provider keys,
     server secrets, login clients), settings, users and roles, or workspaces and their keys.
     People keep all of it, and the UI works as now: `/graphql` moves onto casl abilities too.
   - **Nothing by default.** No entry for `ai-router`, or one with no roles, gives no admin
     tools. Agents must still name `ai-router` in `tools.servers`: it is never in "every server".
     An agent is shown only the tools its roles allow, and the permissions guard every call.
   - **Config is router-wide, runs are the workspace's.** The read roles see every agent,
     provider, pool, server and registry. `runs:read` sees only runs its own workspace started.
   - **A built-in transport.** The `ai-router` row in `servers` is made by a migration, with a
     transport of its own that connects in process (the MCP SDK's in-memory transport), as a
     run's model calls are. The run's workspace and roles are handed over directly. Nobody can
     delete or rename it, or give it a transport, secrets or a login. The UI marks it "Built in",
     and a workspace's entry for it shows its roles instead of env, args and URL.
   - **Drafts.** An `agents:manage` save is a draft, live at once only when the agent has
     auto-promote. An agent may have any number of drafts. Each records the revision it was
     based on and who saved it (a user, or a workspace and an agent). People discard any draft,
     and an agent discards only drafts it saved itself, from the same workspace.
   - **Any user grants roles and turns on auto-promote**, as with every workspace and agent
     setting today. Making both admin-only is a later option.
10. **Later.**
    - Agents offered as MCP tools, on `/mcp`.
    - `/v1/responses` for agents.
    - **Discovery:** the AI Catalog at `/.well-known/ai-catalog.json`, Server Cards, A2A Agent
      Cards, and LAN announce and discovery (servers found on the network, offered to add). The
      public catalog names only endpoints, and agents, servers and cards are listed only to a
      key, for its workspace.
    - Importers for Claude Code subagents, Copilot `.agent.md` and cagent YAML.
    - An agent editor in the UI.
    - **Raw model and tool endpoints**, only if retiring llm-router and mcp-router becomes a
      goal: `/bare/v1` would be a thin door over phase 2's forwarding; `/bare/mcp` is a port of
      mcp-router's endpoint, sessions and elicitation forwarding.
    - **App-supplied MCP servers:** an app passes a server in the request, and the router
      connects to it for that run only, as OpenAI Responses does with `tools: [{ type: "mcp" }]`.
      It needs to be allowed by the override policy, with a list of allowed hosts, because the
      router would be calling a URL an app chose. Until then, an app gives an agent its own tools
      as app tools.
    - **Override policies in full:** more than one, chosen per agent, with a UI.
    - **Import and export** of `.agent.json` and `.agent.md` files, and an
      `ai-router agents push` / `pull` CLI that signs in through the browser. This may be dropped
      altogether.
    - **`POST /runs/<id>/cancel`**, so an app can stop a run it started without dropping the
      stream. That gives `task_server`'s Runs tab a Stop button.
    - **Server groups**, left out of the first pass, to think about later. A group is a named,
      reusable set of servers with their overrides, which many workspaces can include. It maps
      one to one onto an mcp-router workspace. Before adding one, settle two things:
      - a server must reach a workspace only once, or its tool names collide;
      - agents keep naming servers, not groups, so their documents stay portable.

Agents need only the scaffold and models to start, because an agent with no tools is still an
agent. If agents matter sooner than the tools port, phases 5 and 6 can come before 3.

## Open questions

- **Failover and health for pools.** A call whose target can't be reached goes to the pool's next
  target, and that target is passed over for 30 seconds (2026-11-18). Still open: health checks
  that probe a target before a call finds it down, and per-target weights.
- **Model features llm-router lacks:** native non-OpenAI APIs (Anthropic, Ollama's own), and
  cost.
- **An MCP server that asks for input during a run** (elicitation). mcp-router forwards it to the
  app's MCP client, but an agent run has no MCP client to forward to. Phases 6 and 7 decline it.
  Phase 7's waiting runs make the later option cheap: hand the request back like an app tool
  call (an `ai_router` elicitation tool the app answers), and resume as the same run. It needs a
  way for the router's MCP client to hold the request open across the wait, or to answer it
  declined and retry the tool call once the app answers. Worth doing when `min-agent` has a
  server that asks.

- **Long, unattended runs.** A run is one streamed response, and a client disconnecting cancels
  it, unless the request sent an `Idempotency-Key` (phase 6), so a job that retries with one
  survives a dropped connection. The later
  option is to start a run, get its id, and fetch the result afterwards, as Hermes's Runs API
  and A2A tasks do. Proposed: not in v1. The router's own timeouts allow long streams (checked
  2026-11-18: Node's `requestTimeout` covers only receiving the request, and streams get a
  heartbeat), and the README says what a proxy and a client need. The apps' timeouts are checked
  with phase 8.
- **Approval of risky tool calls** (Hermes's command approval). It is not in the model: it needs a
  list of risky tools and a way to ask someone. Proposed: leave it out of v1.
- **Per-tool scoping** (include and exclude lists per server). Proposed: leave it out, so a
  server is the unit.
- **better-auth's organization plugin for workspace keys: no** (reviewed 2026-11-18, better-auth
  1.7). The api-key plugin (`@better-auth/api-key`) can make keys an organization owns, but every
  verify writes the key's `lastRequest`, even with its rate limit off, and the only way to skip
  the database is its secondary storage, which wants Redis or a store of our own. The
  organization plugin's roles are people's roles in an organization, and here every user sees
  every workspace. Phase 9's permission levels belong to an app's server entry for the admin
  server, not to a person, so they can be a column on `workspace_servers` rather than a role.
- **drizzle-graphql, upstream:**
  - It warns about `workspace_keys.hash` and `server_secrets.value` at every schema build: they
    are excluded and NOT NULL, and the warning ignores that those tables' generated inserts are
    switched off. Make the warning respect `features.insert`.
  - A generated update input can't leave out a column: `UpdateServerInput` lists `childUid`,
    `installDir` and `source`, which the hook refuses. Add per-column write exclusion.
  - A field added to a generated type gets only the columns the query selected, and the key only
    when it selected none. `Server.login` and `Server.instances` ask for `id` to be selected.
    Add a way for an added field to name the columns it needs.
- **The spec's own open questions** (agent-level hooks, opt-in bundle parsing, `null` to unset
  an `extraBody` key) touch phase 6. Answer them in agent-core first.
